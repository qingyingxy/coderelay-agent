## 失败原因

这次测试环境准备有遗漏：复制源码时没有建立 Git 基线。
DiffCollector 在 git ls-files 失败后，把现有文件内容包装成 new file mode 100644 的新增补丁。
它没有区分“缺少基线”和“本次真的新增文件”。审查据此将整份解析器误判为超范围重写。

独立前后对比确认初次执行与修复后的差异都仅一行；三份测试的 SHA-256 与执行前相同。
修复模型只是将空值检查改为显式 value === undefined，无法解决父进程的差异基线问题。
不能将这次失败解释为快速模型不会完成任务，也不能把测试通过当作工作流交付成功。

下一步应先保证审查获得任务开始前后的真实差异；缺少基线时应明确报告证据不可用，
而不是假称整个文件是新增。应先离线验证该边界，再考虑是否重测；本次没有扩大范围修复它。

## 基线修复（离线验证）

已修复此次失败涉及的差异证据链路，未新增任务或付费重跑。

- Plan 获批、执行前，按计划中的具体修改路径保存原始文件内容及“原先不存在”的状态。
- 基线保存在当前会话的 delivery-baseline 条目中，按 Workflow 和工作目录校验；恢复会话和修复后复审沿用原始基线。
- 非 Git 文件和已有未提交修改都按执行前后的实际内容生成差异，不再把未知基线假装成新增文件。
- 对新增、删除和无变化文件分别处理；未知路径、读取失败或缺少基线明确标记为差异不可用。
- Delivery Runtime 在差异不可用时终止交付，不启动审查或自动代码修复；独立 Reviewer 入口也拒绝这种证据。
- 未提供捕获基线的旧 DiffCollector 调用仍可读取已跟踪文件的 Git 差异，但必须检查命令成功；不会再将 Git 失败回退成新增补丁。Plan 恢复缺失基线时不使用这个回退。

当前捕获范围是计划声明的具体文件，不展开目录或 glob。文本文件上限为 1 MiB，整份基线为 8 MiB；
超限、二进制或无法读取的内容按证据不可用处理，不能默认为审查通过。
这次接通的是 Plan 交付基线，不代表新 Planner/Executor CLI 已支持跨进程恢复入口。
