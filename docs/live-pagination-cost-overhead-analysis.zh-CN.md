# 直播分页：两组额外开销的离线分析

> 后续已完成 sol 单次补修与共同验收，累计已记录费用更新为 sol $2.35126080、候选 $1.82813728。首次连接超时另有未知费用；见 [补修后的成本对比](live-pagination-sol-completion-cost.zh-CN.md)。下文保留补修前的分析。

## 首要结论：费用差额真实，质量对照存在漏检

sol 直接组记录支出 $1.55292480，最新 sol + luna 组记录支出 $1.82813728，后者多 $0.27521248（17.7%）。离线核实两项缺陷后确认：sol 直接组同时存在首次进入互动页不加载免费资格、采集启动 running 变化未同步 revision 的问题，原审查均未发现；最新候选组经过此前的一次付费修复后，在相同诊断场景下均正常。

使用实际 Vue 页面、同一个模拟轻量接口与非空免费队列做浏览器验证：

| 已有实现 | 直接进入互动页后请求免费队列 | 显示测试用户 |
| --- | --- | --- |
| sol 直接组 | 否，只有 paid 请求 | 否，显示队列为空 |
| sol + luna 修复后 | 是，发起 free 请求 | 是 |

因此，同一审查提示和规则并未带来相同的实际检查覆盖。不能据此声称同等实际质量下双 Agent 更贵，也不能反过来宣称双 Agent 更省。两组通过原固定测试与模型审查是历史事实，审查通过不构成无缺陷证明。

采集启动问题使用两组实际 Python Runtime、同一个带线程屏障的假 Controller 复现。仅替换配置读写和密钥状态查询，未连接采集服务。暂停在 `controller.start()` 将 running 置为 true 之前，从另一线程检查快照是否可进入：

| 已有实现 | 启动暂停时可读取快照 | 客户端已接受状态 | 启动完成 | 按已接受 revision 增量请求 |
| --- | --- | --- | --- | --- |
| sol 直接 | 是 | revision=1, running=false | revision=1, running=true | unchanged=true，漏掉变化 |
| sol + luna 修复后 | 否，受同一锁保护 | 启动前 revision=0, running=false | revision=2, running=true | 返回 running=true |

两个诊断线程均正常释放。证据目录 `.artifacts/live-pagination-luna-max-retrial-20260911/offline-review-parity/`：`results.json` 为既有浏览器诊断，`sol-start.json`、`luna-start.json` 为新增启动诊断。复现只用于离线诊断，未修改冻结验收、业务代码或原始运行报告，也没有进行付费调用。

## 规划：模型较强，但代码依据不足

sol 直接执行没有独立规划产物，不能将其视为“没有规划思考”。其执行记录包含定位、实现方案和复核过程。

本轮独立 Planner 的可见调用只有一轮工具批次：1 次 ls、3 次 find、6 次 grep，然后输出计划，共 2 次模型请求，花费 $0.23012560。

- 两次 find 返回 `fd is not available and could not be downloaded`，Planner 没有补读。进一步检查宿主代码发现，旧 `planner-runtime.ts` 在第一轮工具结束后无条件关闭工具并要求输出计划，错误结果也不例外。补查机会被框架切断，不能仅归咎于模型。
- 业务源码 grep 的 glob 为 `*.{ts,tsx,js,jsx,vue,svelte,cs}`，不包含 Python；没有直接读取 `dashboard_runtime.py` 或 `dashboard_server.py` 的记录。
- 它读取了验收目录内容和前端代码片段，但队列搜索结果被截断；后端计划并非建立在对 Python 实现的直接检查之上。
- 计划要求维护 mutation revision，并提出“集中推进 revision 或比较稳定状态”的备选实现，没有约束为复用现有 `_touch()` 路径。
- 计划列出候选队列分页，但没有列清互动页的免费资格消费路径，也没有指定 collector 启动后 running 与 revision 的同步要求。

sol 直接组同样遇到文件检索错误，但随后用 ls/read 继续定位并检查源码；它没有受到独立 Planner 的单轮调查限制。不能据此证明所有返工由 Planner 引起，但“付费规划没有充分完成关键代码调查、宿主限制阻止回退”已得到代码和记录支持。

## 修改规模：文件少不等于改动小

以下统计来自送入审查的完整 unified diff，新增/删除行不包含 diff 文件头；不是净行数，也不直接等同于复杂度。

| 指标 | sol 直接 | luna 初次提交 | luna 修复后 |
| --- | ---: | ---: | ---: |
| 文件数 | 9 | 8 | 8 |
| 新增行 | 264 | 507 | 541 |
| 删除行 | 40 | 96 | 99 |
| 新增＋删除 | 304 | 603 | 640 |
| Store 新增＋删除 | 67 | 200 | 200 |

luna 初次改动量约为 sol 的 1.98 倍。主要差异：

- sol 保留 dashboard 队列数组，增加请求序号和已加载页记录；luna 引入每类队列独立的 rows、total、page、loading、generation 状态，并同步旧 dashboard 数组，需要维护更多状态关系。
- sol 基本沿用后端事件 `_touch()`；luna 增加 `_revision_state()`，在事件前后深拷贝并比较配置、队列、日志等状态。这与计划中的备选策略相符，但不能证明是唯一原因。
- 新增改动不全是浪费；例如独立队列状态有合理用途。真正可确认的是补丁更大、需要检查的状态关系更多。

## 审查：主要不是测试日志过长

| 指标 | sol 审查 | luna 首审 | luna 复审 |
| --- | ---: | ---: | ---: |
| 模型请求数 | 1 | 8 | 1 |
| 工具调用数 | 0 | 24 | 0 |
| 审查输入 JSON 字节数 | 36,737 | 48,063 | 57,052 |
| 其中测试证据字节数 | 2,342 | 2,405 | 2,405 |
| 累计未缓存输入 token | 15,215 | 39,528 | 20,482 |
| 累计缓存读取 token | 0 | 197,888 | 0 |
| 累计输出 token | 3,824 | 11,061 | 11,138 |
| 费用 | $0.13734000 | $0.45848720 | $0.30468800 |

JSON 字节数不是实际模型 prompt token 数；token 数据来自运行报告的累计用量。输出 token 也不能简单等同于用户看到的文字。

首次审查多出 $0.32114720：候选补丁更大，审查额外执行 15 次 grep 和 9 次 read，核对状态、视图消费者、启动顺序，最终发现两项真实缺陷。不能把这些检查全部当成无效探索。sol 审查零工具调用且漏检免费资格问题，也说明较低审查费用不一定来自更高效率。

测试证据体积几乎一致，没有支持“候选组主要被重复测试日志拖贵”的证据。

复审是新 Reviewer 会话，重新接收相对原始基线的完整 8 文件补丁，加上历史审查摘要；它没有只看此次修复的 2 文件差异。实际修复仅新增 34 行、删除 3 行，但完整补丁新增 541 行、删除 99 行。重新检查完整交付有防止遗漏的价值，同时带来 $0.30468800 的额外开销。改成只看小补丁会有漏检风险，不能直接当成等价优化。

## 修复：小补丁也会产生较多调查成本

唯一一次修复花费 $0.66714000：12 次请求、35 次工具调用，其中 22 read、8 grep、2 find、3 edit。

- App.vue 读取 6 次，dashboard_runtime.py 读取 4 次；读取包含不同片段及编辑后的复核，不能全算重复浪费。
- 还检查了 controller、router、QueueTable、样式、类型与测试。修复从新会话开始，需要重新建立代码理解。
- 修复先提出启动后补 revision，复核时再调整为启动与 revision 推进在同一锁区间内，存在方案细化开销。
- 修复输入与缓存累计约 560,553 token，输出 10,872 token；这不是一次性上下文大小，而是多次请求累计。缓存读取收费约 $0.19916800，仍占修复费用近 30%。

## 费用归因与行动顺序

| 组成 | sol 直接 | sol + luna |
| --- | ---: | ---: |
| 规划＋初次执行 | $1.41558480 | $0.39782208 |
| 首次审查 | $0.13734000 | $0.45848720 |
| 修复 | $0 | $0.66714000 |
| 复审 | $0 | $0.30468800 |

规划＋执行节省 $1.01776272；首审额外开销、修复和复审合计多 $1.29297520，最终净多 $0.27521248。不能将 $0.66714 全部归因于计划，也无法从一组记录中精确拆分“必要调查”和“可避免重复”的费用。

建议顺序：

1. 先校正对照可信度：对同任务任一组已证实的 must-fix，离线核对另一组，避免将模型漏检当作低成本成功。暂不新增付费比较。
2. 再补规划的代码依据：关键文件有成功读取证据；检索失败或输出截断后补读；覆盖接口消费者和状态变更入口。这比继续加长计划更直接。
3. 优先复用既有状态模型；引入额外状态副本或全量比较前说明必要性，减少执行模型自行选择复杂实现的空间，不按行数硬限写入。
4. 给修复/复审提供具体缺陷、定位、修复差异和仍有效的完整基线证据，减少重新搜索；保留必要的完整回归检查，不直接降低模型档位或审查要求。
