## 为什么候选仍然被停止

实际链路为：

1. `WorkflowController.startPlan` 创建根任务时，调用 `inheritBudgetLimits(budget, BUILTIN_AGENT_PROFILES.planner.defaultBudget)`。
2. `inheritBudgetLimits` 会把 Profile 中的 240000ms 和 12 轮默认值重新带入根任务。
3. `AgentSession._runPlannerWorkflow` 把 `rootTask.budget` 原样传给 `executePlannerPrompt`。
4. 执行器虽然已经不再主动补默认值，但把这个上游合成的值当成显式预算，于约 240 秒主动取消请求。日志留下 `planner_stop / planner.max_duration`，而不是网络超时。

这是上次修正和本轮冻结核对遗漏，不是 luna 执行失败。只测试 `executePlannerPrompt(..., {})` 能越过旧限制，不能证明真实 `startPlan → rootTask → executePlannerPrompt` 入口也能越过。应撤回“Planner 实际入口已经完全移除隐含 240 秒限制”的结论。

本轮没有改变冻结框架后重试，没有人工补业务代码，没有追加付费排障。候选组没有修改原始业务文件。

## 下一步的最小边界

本轮 sol 的通过代码与 $1.7682824 交付费用保留作为事实记录；若后续修改框架后补候选组，必须注明与本轮框架不同，不能包装成同一冻结版本的新对照。是否重启完整配对试验，应在离线入口回归通过后再决定。
