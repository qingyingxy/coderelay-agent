# 队列取消评测报告与后续测试计划

日期：2026-09-09。范围：任务队列取消样例及一次受限修复。

## 结论

强模型规划、快速模型实现的候选方案，在一次人工指定问题的受限修复后，通过了 9 项测试和独立复审。候选累计模型费用为 $0.20805232，低于已成功交付的强模型基线 $0.27564400，差额 $0.06759168，约 24.5%；累计运行耗时更长。

这是一个已知样例上的探索性恢复结果。尚未证明稳定节省、强模型规划的独立收益、生产流程的自动恢复能力或真实长上下文连续性。

## 目标与验收范围

验证在实现工作量增加后，快速模型的执行节省能否覆盖规划、审查和返工开销，同时保持交付质量。

样例为本地、无外部依赖的任务队列，涉及 queue、runner、store 三个模块。验收覆盖排队取消、运行中取消、中止信号、晚到结果、并发名额、FIFO、状态通知、快照和空闲等待。不涉及持久化、重试功能、网络服务或通用输入加固。

初始验收有 7 项测试；经实际审查发现两个符合原任务要求的漏测场景，先后增加到 8 项和 9 项。历史结果按原协议保留，没有以新测试改写旧记录。

## 修复了什么

第一处：enqueue 在把任务放入 pending 之前就通知订阅者。订阅者立即调用 onIdle 时，误认为队列为空。补入回归后，v3 候选修正了此问题。

第二处：候选在登记 AbortController 前发布 running 状态。订阅者立即 cancel 时，公开状态变成 cancelled，但没有控制器可中止。受限修复将控制器登记提前到 running 通知之前，只改动 queue.mjs 和 runner.mjs。

两个问题均已通过独立离线案例复现；保存的强模型基线在对应案例中行为正确。它们是原任务中的状态一致性缺陷，不是为了阻止交付追加的库级加固要求。

## 证据与限制

- v3 两组的初始代码、任务、测试和上下文配置摘要一致，受保护文件及文件清单保持不变。
- 修复前，保存的候选代码通过 8 项、只失败新增第 9 项；保存的基线通过全部 9 项。没有重新付费生成基线。
- 最终修复通过 9 项父流程测试；复审返回 review:passed、review_findings:[]，无未完成事项。
- 队列执行没有发生切窗，不能支持切窗效果或长会话恢复率的结论。
- 候选使用现有 Planner/Executor 入口；最终统一审查由评测脚本执行。修复由人工指定故障并启动新的快速模型会话，不是生产自动恢复链的验证。
- 新增回归和故障说明是在观察失败后提供的，人工诊断劳动未折算进模型费用。这不是双方从一开始按 9 项固定验收进行的全新随机配对试验。
- 费用来自本地模型配置费率，不是账单；阈值不是硬账单上限。模型缓存、输出长度及随机性可能影响结果。
- 没有快速模型直接执行对照，无法把收益单独归因于强模型规划。一个已反复调试的样例不能代表其他任务。
- 当前目录内的模型执行使用 shell 工具，不具备操作系统级文件隔离；完整性检查是结果验收，不等同于预防性沙箱。

## 下一步一：先验证自动闭环，暂不付费

下一步最优先的问题是：能否无需人工重新描述故障，自动把有证据的审查问题交给执行模型，修复一次后重新验收。

用已有 faux provider 和固定命令结果覆盖以下路径，不增加业务功能：

| 场景 | 必须观察到的行为 |
| --- | --- |
| 测试失败 | 真实命令结果进入恢复上下文；不能以模型自述覆盖 |
| 有证据的 must_fix | 只传问题、定位证据、授权文件和原验收；最多一次修复 |
| 修复完成 | 针对新代码重新执行测试和审查，旧版本结果不复用 |
| 修复仍失败 | 停止并保留失败报告，不扩大范围或追加无限重试 |
| 全部通过或仅有建议 | 正确交付，不把“确认正确”误作等待用户决定 |
| 真正需要用户决策 | 停止自动修改，问题明确，不静默放行 |
| 预算用尽、模型或审查报错 | 报告明确终止原因和已发生费用，不漏计、不误判成功 |

目前 repair 模式绑定历史 v3 路径，并用已知基线费用计算剩余空间，只适合这次恢复实验。后续正式评测需接收运行输出与证据作为参数，提前固定预算，不依赖先看到另一组的费用。应复用现有恢复与审查逻辑，不另造复杂调度系统。

先决定并记录修复模型政策。建议首轮固定为各组原执行模型修复一次；生产中的强模型升级策略另做试验，不在运行中临时改变。这样既能验证本次“快速模型受限修复”的想法，也能明确它与现有生产升级规则的差别。

## 下一步二：三组小规模对照

自动闭环离线验证通过后，先用当前 9 项验收做协议稳定性检查：

| 组别 | 作用 |
| --- | --- |
| 强模型直接执行 | 质量和总成本基线 |
| 快速模型直接执行 | 判断便宜模型是否本身就够用 |
| 强模型规划、快速模型执行 | 判断规划新增费用是否换来更少错误和返工 |

每组从干净初始目录运行 3 次，共 9 次主运行。测试、独立审查、工具范围、上下文政策和最多一次修复规则一致。交替或随机安排顺序并保存随机顺序，避免把时间段差异都归到模型上。所有样本保留，不挑最便宜的成功结果。

建议每次主运行含修复、复审共用 $1、10 分钟停止阈值；9 次的名义预算阈值合计 $9。此处只是待批准的测试建议，不是已执行或已授权的新费用。先完整跑一轮三组，只有流程正常才继续剩余两轮；协议错误先修脚本并显式换版本，不能只重跑不利样本。

必须记录：首次通过数、最终交付数、修复次数、所有尝试总费用、各阶段费用、耗时、切窗次数和失败原因。报告每条原始结果与范围，不用三次样本宣称统计显著。

整体交付成本采用“所有尝试总费用 / 成功交付数”，把失败消耗算入；零成功时报告无成功交付，不能算作零成本。修复属于同一尝试，不能再计一次成功。还要单独列成功率，避免低质量方案看起来更便宜。

判断：候选必须在保持交付率的前提下低于强模型总成本；若快速模型直接执行同样可靠且更便宜，就没有理由在这类任务上默认付费规划。

## 下一步三：新任务与切窗分开验证

队列已多次用于调试，后续不能只在这一题上证明泛化。准备两类未用于调参的任务，每类先跑三组各一次，再决定是否扩样：

- 中等实现任务：例如给现有批量导入工具加入逐条校验、错误聚合和原子提交；验收明确，涉及多个模块，无外部服务。
- 缺陷修复任务：选择本地可复现、带独立验收的跨模块缺陷，例如缓存失效导致旧值泄漏；不靠增加无关代码制造长度。

入选前固定要求、排除项和测试；用参考实现和针对关键错误的变异检查校验测试能力。出现新的真实合同缺陷时记录测试缺口，另建协议版本，不把旧结果偷偷重新归类。可保留独立隐藏测试，但评分只依据预先明确的要求。

切窗单独做连续性测试，不混入路由收益归因。先做离线强制边界测试：计划版本、已完成切窗次数、已有补丁、未验证事项和历史引用在新窗口可见；旧测试通过不能覆盖新修改；多次请求不能重复完成同一切窗。

离线通过后，在同一执行模型、相同任务和验收下，对比不主动切窗与在明确执行点切窗一次，计入交接、历史查询和额外读取费用。成功标准是边界确实发生、任务继续且交付正确、未丢失待办；应标记为强制切窗试验。之后才选自然达到上下文阈值的真实任务，验证实际触发。没有触发就如实记零，不能称为长上下文验证。

## 本阶段暂不做

不增加 Worker 并行，不继续扩展计数器或队列库，不为了提高通过率放宽审查，也不一次上大规模付费基准。先验证自动恢复和规划是否有独立价值，再决定复杂任务路由规则。Git Worktree 并发、进程崩溃恢复与自然长会话效果应作为独立能力验证，不能从这份报告推导已经完成。
