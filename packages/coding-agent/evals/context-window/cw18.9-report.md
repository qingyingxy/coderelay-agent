## Protocol

Reserve four worst-case requests for initial verification, one repair,
reverification/commit, and a final reply. Initial configuration must also
afford one implementation request. The previous 64k/4k price configuration
therefore requires at least $1.040 initially ($0.208 per request), up from the
v2 minimum of $0.624. Existing per-trial limits are not increased automatically.

Calling container_submit closes ordinary implementation, even before reaching
the reserve threshold. The first failed verification opens the repair stage
only when three future requests remain affordable. Only container_repair is
available there; its single command uses the existing 60-second, bounded-output
container bridge. The command consumes its allowance even if it returns failure.
At execution time it must still leave capacity for reverification and a final
reply. The next stage permits only container_submit with the original,
byte-identical verification command. Successful verification permits commit.

Repeated verification failure, commit failure, or insufficient repair capacity
closes submission. Closed stages expose no tools. Execution guards reject
out-of-stage calls even when the model emits them anyway. Ordinary execution
and memory tools cannot consume closing capacity; automatic context maintenance
is disabled when submission begins. Provider requests remain budgeted without
automatic retries, including requests wasted on invalid tool calls.

The budget notice includes the submission stage, attempt/repair counts,
original verification command, and any recorded closure reason. Runtime results
retain those counters and reasons. submission-attempts.jsonl preserves failed
and successful attempts instead of only the latest submission.json; repair.jsonl
records the repair command and its result.

## Failure coverage

Targeted Faux regressions cover successful repair, repeated verification
failure, a failed repair command, attempts to change the verification command,
duplicate repair calls, and capacity lost before repair. They assert that
blocked commands never reach the executor and failed verification never stages
or commits. Initial request-count and cost shortages are rejected. Existing
tests also cover commit failure, missing submission, unauthorized ordinary
execution during reserve, request accounting, and A/C memory/routing behavior.

The real Docker fixture begins with incorrect file content. The same content
check fails before repair and succeeds afterward; the smoke explicitly verifies
that the first attempt did not change HEAD. Five scripted model requests produce
five model-requested container calls/replies: write, verify, repair, reverify,
commit. Diagnostic and capability probes are additional bridge operations.
