## Findings

1. The previous approval block is resolved. Direct execution created a branch,
   inspected code, and edited files. No approval wait was emitted.
2. Tool assumptions wasted requests: `apply_patch` was unavailable, `git apply`
   received a corrupt patch, and two `patch` calls failed on malformed patches.
   A later editor-availability probe also returned nonzero. The model eventually
   used Perl edits and Python syntax checks. These are execution/tool issues,
   not evidence of memory loss.
3. The request ceiling, not the dollar or time ceiling, stopped this trial.
   No commit command was issued, so the official patch was empty. The current
   system prompt requests a final commit but supplies no remaining-request
   countdown or reserved model turns for verification and submission.
4. A context warning was emitted only after the first request-limit error and
   `agent_end`. It reported 45627 tokens, a 38400 soft limit, and a 51200 hard
   limit. The ensuing continuation was denied by the already exhausted budget.
   The model thus had no successful response opportunity after that warning.
   Do not describe the absence of Notes/new_context as ignoring a timely warning.
   Audit warning scheduling during a continuous tool loop with a free regression
   before drawing conclusions about autonomous memory decisions.

## Next steps

First use free tests to validate continuous-tool-loop warning timing and budget
awareness. Define an explicit, identical A/C tool capability contract and a
budget-aware verification/submission phase. Preserve interrupted working-tree
evidence separately from the official HEAD patch; do not retroactively commit
or rescore this failed trial. Any changed execution protocol needs a new version.

Then reassess the request ceiling and aggregate budget for a fresh pilot.
Increasing the request ceiling alone does not fix tool assumptions, missing
submission time, or late memory warnings. There is still no matched long-task
