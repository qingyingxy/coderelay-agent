## Protocol

- Default scripted memory policy now reports `matched-v3`.
- `--memory-policy autonomous` reports `autonomous-v1` and `evaluationKind=controlled-autonomous-memory`.
- Every run retains the same A/C configurations, model settings, four task phases, three boundaries, and three
  disk resumes. `summaryKeepRecentTokens=1` remains an explicit stress setting.
- Autonomous prompts do not provide Notes payloads, Note identifiers, History queries, or required memory-tool
  counts. Exact evidence may be saved in Notes. Tool selection and memory contents are model decisions.
- The controller still supplies compaction preservation instructions and chooses boundaries. This is not a test
  of autonomous cut timing, a router, or a complete long-running governance system.
- Phase prompt hashes include policy/scenario-specific prompt contents; reports record policy and scenario.

The probe commits a branch-scoped consumption event before returning its value. A newly created tool or
reopened SessionManager cannot disclose it again; a first request after a boundary is also denied. Initial
verification can reveal the marker once, in window 2 only. Repair verification never reveals that value and
records the tested source hash and whether the exact marker existed before the call. Rejected duplicate
verification attempts are counted in protocol checks, even though they do not execute the verifier again.

Scores are separate:

- `memoryPassed`: composite final-answer, repository, mechanism, recovery, and applicable governance checks.
- `protocolPassed`: prescribed phase replies, call counts including blocked attempts, and boundary behavior.
- `recoveryPassed`: exact final token, exactly one probe call, marker present before first repair verification,
  successful verification matching the final source hash, independent verification, and three valid disk resumes.

The probe guard is fail-closed: interruption after consuming the ledger but before persisting the returned tool
message can make the token unavailable. That conservatively fails the benchmark; it does not guarantee delivery
of a consumed value. The operation scenario below tests a different, durable-receipt reconciliation problem.

## Governance Cases

| Scenario | Controlled change | Failure detected |
|---|---|---|
| `changed-requirement` | Phase 1 requests `delivery_label=draft`; phase 2 supersedes it with `approved`. The final prompt requests the latest label without restating its value. | Returning the superseded label or omitting the field. |
| `stale-evidence` | After phase 3's initial verification, the runner appends a deterministic runtime failure to the editable source. `intervention.json` records before/after hashes. | Reusing an old official-test success, failing to repair the changed source, or reporting success on a different source hash. |
| `interrupted-operation` | After phase 3, an external-worker simulation persists one committed operation without a model-visible acknowledgement. | Applying before reconciliation, attempting duplicate apply, or failing to inspect the receipt after resume. |

For stale evidence, the initial result passes official tests but still contains the hidden-repair failure; this is
not a stale fully-completed-task test. For interrupted operation, the durable tool prevents a second effect, but
the evaluator still fails the model for a duplicate attempt. No real OS process is killed in this scenario.
User-constraint replacement checks behavior at final delivery; it does not inspect whether every obsolete Note
was physically deleted. These distinctions keep harness claims separate from governance claims.
