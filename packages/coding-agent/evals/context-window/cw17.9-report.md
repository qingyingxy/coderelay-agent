# CW.17.9 Matched-Prompt A/C Evaluation

## Validity Correction

This historical `matched-v1` evaluation included the expected `memory_token` in the final phase prompt. Its token
answer checks therefore do not demonstrate long-range recall. The raw results below are retained for audit, but
the reliability conclusions must be read with this limitation. Repository repair, hidden marker, and persistence
checks remain separate evidence. Notes and History calls were scripted, and summary used `keepRecentTokens=1`;
this was a controlled stress test rather than an autonomous or ordinary-default comparison. The runner now uses
`matched-v2`, which withholds hidden answers from every phase prompt. The completed corrected matrix and its
failure audit are documented in [cw17.10-report.md](./cw17.10-report.md). That report supersedes the decision and
next-gate recommendations below; historical measurements remain unchanged for audit.

## Decision

Keep `summary` as the global default for now, but advance the Workflow-specific `hybrid` route to the next decision gate. Under matched phase prompts and matched controller boundaries, C=`windowed + Workflow Snapshot + Notes + History` was more reliable than A=`summary`, finished faster, and cost approximately the same. The current task set still contains only three small, scripted repositories, so it is not sufficient evidence for a global default change.

## Fairness Correction

CW.17.8 compared a controller-triggered C group against an older A baseline that sampled three artificial `WINDOW_n_READY` turns. CW.17.9 removes those sampled boundary turns from both primary groups:

```text
phase completes
  -> runner invokes summary compaction or hard cut
  -> Session JSONL is reopened
  -> next matched phase prompt is sent
```

A and C receive byte-identical phase prompts from one function. Notes and History instructions are conditional on tool availability, so the text is unchanged even though the tested tool sets differ. `report.json` records `phasePromptProtocol=matched-v1` and one SHA-256 fingerprint per task:

## Failure Analysis

The A failures were not boundary-runner failures:

1. Repeat 3 / LIS failed repository memory. The third generated summary retained that `HIDDEN_REPAIR_REQUIRED` requested a marker but dropped the exact marker line despite the compaction instruction. The model inserted the recovered value as an indented local variable instead of the required top-level line, returned the expected JSON, and failed the independent verifier.
2. Repeat 2 / LIS and repeat 3 / Sieve passed final independent verification and returned the exact long-range token, but called repair verification before writing the recovered marker. They therefore passed memory/repository grading and failed only the phase protocol.

The first smoke exposed a scoring problem: a summary boundary intentionally retains its recent Assistant suffix, while a hard cut excludes it. The runner now validates each strategy's declared active-context shape instead of requiring summary to mimic hard-cut exclusion. Model-requested repair verification order is also reported as protocol behavior; independent final verification remains the memory/repository authority.

## Conclusion

This matched-runner result removes the main confound in CW.17.8. On the current tasks, hard cut plus Workflow Snapshot, Notes, and raw History improved memory reliability and phase adherence at essentially neutral cost, with lower output volume and shorter elapsed time. It also demonstrates the intended architectural advantage: exact evidence remains recoverable even when a generated summary paraphrases away syntax-critical detail.

The next gate should add at least two larger, longer, less scripted repository tasks and compare A/C with the same `matched-v1` protocol. If C remains no worse on completion and cost, CW.18 should make `hybrid` the default for active Workflows while retaining `summary` for ordinary conversations.
