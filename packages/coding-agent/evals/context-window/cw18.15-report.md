# CW18.15: Successive handoff retention and omission boundary

Date: 2026-09-06. Free Faux Provider regressions only; no paid run or host commit.

## Finding

The current free-text replacement mechanism does not guarantee that unresolved
requirements survive a model-authored omission. Existing-suite success does not
automatically delete a pending item, but a later handoff can omit it and replace
the current brief. History retains the old brief. This reproduces the boundary
observed in CW18.14; it is not evidence that omission has been eliminated.

## Minimal Change

Clarified the existing `new_context.handoff` parameter guidance and the Seed's
verification guidance: carry unresolved items into each replacement brief unless
item-specific verification evidence or an explicit user scope change resolves
them. Passing the existing suite alone is insufficient; uncertainty remains
unverified. Unresolved items still go first within the existing byte limit.

No schema, status machine, summary model, new Agent, platform, semantic parser,
automatic brief merger or submission gate was added. Handoff replacement,
Snapshot persistence and History retrieval semantics are unchanged. Prompt
wording is a behavioral instruction, not runtime enforcement.

## Free Cases

`test/suite/agent-session-handoff-continuity.test.ts` uses the existing harness
and Faux Provider. Each case makes three context cuts and seven scripted
provider calls, with synthetic existing-suite and targeted verification tools.
Evidence references use actual Session entry IDs. No summary call occurs.

| Case | Observed result |
|---|---|
| Carry pending item while existing suite passes | Pending item remains in subsequent Seeds and replayed task brief |
| Omit the optional handoff parameter | Previous brief, including pending item, remains |
| Run targeted verification and replace pending text with its evidence | New verified wording and real tool-result reference are preserved |
| Replace brief with only existing-suite success | Omission is accepted despite zero targeted checks; pending item disappears from current Seed but remains queryable in History |

The last case deliberately asserts the known limitation. A green test means
the limitation is reproducible, not that the desired no-omission guarantee
passed. The positive cases script compliant replies; they do not measure
whether a real model follows the new instruction or estimate its failure rate.
User scope-change handling is guidance only, not a tested semantic mechanism.

All cases verify unchanged running workflow state at the third cut, no tool
errors, three completed cuts, no compaction, empty Notes, History retrieval of
the original pending text, and replay of the final task description.

## Interpretation

The prompt now explicitly describes the missing carry-forward rule and the
tests preserve both the compliant path and counterexample. Deterministic tests
alone cannot prove semantic adherence by a real model. No new quality baseline
or readiness for routing is claimed. No additional paid trial was launched.
Any future requirement for a hard guarantee would need a separately justified
change to the representation or validation of unresolved work; it is outside
this minimal prompt-and-test change.
