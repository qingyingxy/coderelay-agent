## A's Seven Failures

Four parameterized `test_rolling_quantile_expr_lazy_ungrouped` cases fail for
Polars eager, PyArrow, Pandas and Pandas/PyArrow. Required usage is
`rolling_quantile(window_size, *, quantile=...)`; A implemented public APIs with
positional `quantile` and keyword-only `window_size`. Calling
`.rolling_quantile(3, quantile=0.5, ...)` raises a duplicate-argument TypeError.

Three validation cases fail the explicitly required exception-message prefixes:

- Negative/out-of-range quantile: A emits lowercase `quantile must be between
  0.0 and 1.0`, while the requirement specifies `Quantile must be between 0.0 and 1.0`.
- Invalid interpolation: A emits `Unsupported interpolation method: 'bad'`,
  while the requirement specifies `Interpolation must be one of`.

A's summary generalizes validation requirements and omits those exact strings.
Neither exact prefix appears anywhere in its captured post-maintenance context;
both appear in C's captured Seed. Neither captured post-maintenance context
contains the literal original `rolling_quantile(window_size` signature string.
This is a concrete information-retention observation, not an automatic prose
quality score. C also consulted History. Implementation choice, test selection
and sampling remain confounders; one pair cannot prove summary omission caused
all seven failures or that handoff alone explains the score difference.

A performed additional manual interpolation and Decimal checks, yet its local
tests did not catch the public call-shape/message-contract errors. More requests
or numerical examples did not guarantee full requirement coverage. Both models
encountered unavailable Ruff, and neither received host dependency assistance.

## Verification And Interpretation

Both local submissions selected their new order-statistic test file plus the
existing rolling_sum tests. C also compiled the relevant Python files. Neither
final local command was the whole independent verifier. Original regressions
passed under the pinned grader in both arms; baseline skip/xfail/backend limits
from CW18.24 still apply, including absent Dask. Successful pinned scoring is
not universal correctness across every optional backend or unavailable lint tool.

This pair supplies evidence previously missing: actual maintenance followed by
substantial real-model execution and independent final acceptance. On this pair
C scored higher, used fewer requests and lower estimated cost. Preserve it as
a first controlled baseline, including A's failure and C's gate rejection.

Do not infer a routing policy or general strategy superiority from one pair,
or compare these continuation-only costs directly with from-scratch CW18.25.
Further comparisons should repeat the fixed protocol across additional seeds
or tasks, without patching the prompt with these known failures. No additional
trial or framework change was performed here.
