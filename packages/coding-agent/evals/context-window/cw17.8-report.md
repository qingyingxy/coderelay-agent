# CW.17.8 Controller-Triggered Hard-Cut Evaluation

## Decision

Keep `summary` as the global default. The controller-triggered hard-cut group passed every memory and repository check, removed model-trigger variance from the primary metric, and was cheaper than the reused CW.17.7 summary baseline. The task set is still too small, and the cost comparison includes fewer boundary-protocol model calls, so it is not sufficient to change the default.

## Protocol Separation

CW.17.7 mixed two questions in one strict result:

1. Can Snapshot, Notes, History, Session JSONL, and hard-cut reconstruction preserve enough state to finish the task?
2. Does the model call `new_context` exactly when requested and perform no unnecessary action after the cut?

CW.17.8 reports them separately as `memoryPassed` and `protocolPassed`. The primary C matrix uses `--boundary-trigger runner`: each phase completes, the runner requests the hard cut, and the next process-level resume starts from the persisted boundary. `new_context` is not exposed in these runs. An opt-in `--boundary-trigger model` mode separately counts model-trigger opportunities, misses, duplicate calls, runner fallbacks, and post-cut tool actions.

Runner-triggered cuts after a settled Direct Workflow now checkpoint the latest settled Direct Workflow in `windowed` mode. Branch navigation clears that retained provider, and `hybrid` routing still treats only an active Workflow as eligible for hard cuts.

A future default-mode gate must run both strategies with controller-triggered boundaries in the same runner version.

## Model-Trigger Evidence

The original CW.17.7 C matrix recorded 27/27 model-triggered boundaries and no duplicate `new_context` calls, but 6/9 runs made one redundant read-only probe after a cut. The first post-projection-fix smoke later missed one requested `new_context`; the second triggered all three.

One CW.17.8 `--boundary-trigger model` smoke exercised the new independent counters:

| Metric | Result |
|---|---:|
| Model-trigger opportunities | 3 |
| Model-triggered cuts | 2 |
| Runner fallbacks | 1 |
| Model-trigger misses | 1 |
| Duplicate `new_context` calls | 0 |
| Post-cut tool actions | 0 |
| Exact boundary replies | 3/3 |

The fallback preserved three Snapshot-backed boundaries and allowed the final phase to run. Its last Provider call raised estimated cost from below the `$0.25` pre-call limit to `$0.261733`; the runner then stopped before recording the final response and independent verification. Its memory result is therefore ungraded due to the budget stop, not evidence of memory failure. No further paid run was made.

## Conclusion

The hard-cut memory architecture is stable under deterministic controller boundaries on this task set. Snapshot, Notes, History, full JSONL retention, active-history replacement, and process-level resume all passed repeatedly. Model-triggered proactive cuts remain useful, but their instruction-following reliability must be reported separately and protected by controller threshold/fallback behavior. CW.18 should keep `summary` as the global default and leave `windowed`/`hybrid` opt-in until a same-runner A/C comparison covers larger repositories and longer, less scripted work.
