## Failure Analysis

Four added test functions cover checkpoint bookkeeping, safe-insert failure,
invariants/CSV/JSON, and CLI insert/bulk UPDATE. They contain no safe-upsert API
or CLI upsert call. The checkpoint lifecycle/nesting test creates checkpoints
and finalizes them without inserting rows between creation and finalization.
It therefore misses the write-induced savepoint loss exercised by official tests.

Official failures comprise six checkpoint cases and four upsert cases:

- `test_rollback_to_checkpoint`
- `test_commit_checkpoint`
- `test_nested_checkpoint_handling`
- `test_nested_savepoints`
- `test_checkpoint_not_active_after_rollback`
- `test_checkpoint_inactive_after_commit`
- `test_safe_bulk_upsert_with_validation`
- `test_safe_bulk_upsert_with_validation_failure`
- `test_safe_bulk_upsert_strict_mode_with_invariant_failure`
- `test_cli_upsert_safe_mode`

Checkpoint and API upsert traces show `no such savepoint` on release/rollback;
the strict upsert case loses the required validation wording when rollback
raises. CLI upsert returns exit 1 where 0 is expected. The submitted patch only
suppresses selected connection-context commits while `_safe_import_depth` is
positive; standalone checkpoint creation does not increase this depth. This
explains the ordinary-write checkpoint vulnerability visible in the traces.
No post-grading repair or new reproduction run was made.

Normal local repair did occur: an ordering assertion failed, was made
order-independent, and the selected tests passed. Full-suite documentation
checks subsequently failed; the agent regenerated the reference without the
missing cog tool and added command examples before rerunning the full suite.
Submission reran `pytest -q` successfully and committed
`578ba59691e443b081f9565389897b870a4f53c2` on `safe-import` in the disposable
target repository. There was no host repository commit.

## Interpretation And Next Step

CW18.14 scored 56/60 feature tests; this run scored 50/60. These are individual
observations with different model trajectories, not evidence that the new
prompt lowers success rates. No matched A trial or repeated comparison ran.
The 0.99089 mixed partial score is dominated by preservation tests and must not
be reported as a task success rate.

The full recovery mechanism operated, yet the implementation and verification
choices were insufficient. Available and repeatedly recovered requirements
did not become adequate tests. This does not establish that context cutting
caused the defects, nor that the memory framework is reliable in general.

Retain this failed end-to-end sample. The next comparison should freeze the
current configuration and use the existing A summary strategy on the same task
under a separately agreed aggregate budget, followed by matched repetitions
if justified. A is a summary strategy, not a no-cut control. Do not inject these
hidden failure names into a future baseline prompt, automatically repeat C
until it passes, or add a new memory architecture based on this one result.
