## Submission failure

The model-authored `tests/test_safe_import.py` inserts two rows into `items`,
then registers `select count(*) = 2` as an invariant and expects it to pass.
The original task explicitly requires SQL beginning with SELECT to be executed
as supplied. Without a FROM clause, this query does not count the table's rows
and returns false. The intended test query is:

```sql
select count(*) = 2 from items
```

The local verification stopped on this assertion (1 failed, 2 passed).
`container_submit` correctly did not commit. The model's final visible reply
identified the missing FROM clause and acknowledged unfinished CLI/docs work.
This specific failure is a test expectation error; correcting it would not by
itself demonstrate complete or correct implementation.

Before request 30, the budget notice showed $1.3601832 spent and three
conservatively affordable requests. Requests 31 and 32 were in submission phase,
which permits only `container_submit`. The model could diagnose the failure but
had no explicit ordinary execution step for repair. Neither the 100-request
ceiling nor the wall-clock timeout was reached.

This exposes a limitation of the current reserve: it provides verification and
commit capacity, but no explicit verification-failure repair stage. Do not
work around that restriction by embedding repairs in a verification command,
retrospectively commit edits, or replace the recorded official result.

## Next work

First design and free-test a bounded verification -> repair -> resubmission
transition, with explicit repair capacity, allowed tools, maximum attempts, and
the same overall cost cap. Verification must still pass before commit, and
exhaustion must remain an incomplete result. Include failing verification,
successful bounded repair, repeated failure, and insufficient-budget cases.
Then review a fresh single-trial budget before any further paid run. A matched
A/C matrix and routing decisions remain premature.
