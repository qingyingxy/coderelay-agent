## Failure Audit

All seven composite failures were A runs. Evidence is in the corresponding `result.json` and Session JSONL;
the summary IDs below locate the final compaction evidence.

| Run | Evidence and observed outcome |
|---|---|
| Repeat 1 / LIS | Summary `9370b1e7` retained token but omitted marker. Model called repair verification before adding the exact marker, learned it again from the failure, then repaired the file. Independent verification passed, but final status remained `verification_failed`; composite and protocol failed. |
| Repeat 1 / RPN | Token absent from all three summaries, including final `8447e59f`; final `memory_token=null`. Repair and protocol passed. |
| Repeat 1 / Sieve | Summary `0c90e28e` retained token but omitted marker. Model stopped without repair or final JSON; independent hidden verification failed. This is not evidence that the token itself was lost. |
| Repeat 2 / LIS | Summary `dfed3e1d` retained token but omitted marker. Model stopped without repair or final JSON; independent hidden verification failed. |
| Repeat 2 / RPN | Summary `42e2f045` retained token but omitted marker. Model first used token as a guessed marker, then obtained the true marker from failed repair verification (`eb756d58`). It inserted the assignment inside the function, failing the exact-line verifier, yet reported `passed`. This combines evidence loss, reacquisition, incorrect repair, and unsupported completion reporting. |
| Repeat 3 / LIS | Summary `070dccc5` contained neither exact value. Model explicitly stopped because both were unavailable; no repair or final JSON. |
| Repeat 3 / Sieve | Summary `4b2deb8d` retained marker but omitted token. Repair and protocol passed; final token incorrectly contained the repair marker. |

Across A, the last summary retained the token in 6/9 runs and marker in 4/9. Final token answers were correct
in only 4/9 because two token-retaining runs stopped for a missing marker without returning JSON. Thus final
token scoring, summary retention, independent repair, and protocol adherence measure different things.
The two A runs passing both composite and protocol were repeat 2 / Sieve and repeat 3 / RPN.

## Smoke, Cost, And Validation

Smoke passed the composite in both groups, but C failed `probe-called-once`: its second probe occurred after
boundary 2 (entry `d1076097`). It therefore does not establish uninterrupted three-boundary token recovery.
The probe remains callable in the harness; repeated calls are rejected by protocol scoring rather than blocked.
The formal matrix avoids this ambiguity because every run called the probe only in the first window.
Similarly, the verifier can reveal the marker again: independent final verification alone is not proof of recovery.

## Scope Of The Baseline

This matrix fixes the final-prompt answer leak and supplies auditable evidence for the tested bundle. Do not pool
it with `matched-v1`, or attribute the historical-to-current difference solely to the prompt fix: the model samples
were rerun, and other working-tree/service conditions were not a controlled intervention.

Notes content and History queries are scripted; the controller chooses every boundary. Summary retention is an
extreme stress setting. C differs in Workflow state and tool access as well as cut strategy. These results therefore
support this bundle's recovery under the recorded conditions, not an isolated hard-cut effect, default-policy
superiority, autonomous write/invalidation/conflict handling, or production long-task reliability.

Use this frozen baseline for regression comparisons. A future harness version should prevent repeated probe
disclosure and distinguish marker recovery from verifier-assisted reacquisition before pooling further trials.
Ordinary retention settings, less scripted tasks, changed user requirements, stale code evidence, and routing
decisions remain separate evaluation gates. This report does not implement or validate those gates.
