## Text Pressure And Limits

Twenty of 24 briefs are exactly 2000 bytes, and many end mid-sentence or
mid-expression. Neither arm received extra model requests. Provider results
ended as tool calls, not `length` stops. The local runner validates the byte
limit and trims surrounding whitespace; it does not slice the handoff text.
The saved responses do not establish whether the abrupt boundaries originate
in model generation or upstream service/tool-schema processing.

Implementation descriptions, generic review advice, and branch/commit checks
consume much of the brief. That is observable content allocation, not proof
that the byte limit alone caused every omission. The excerpted observations do
not prove branch creation, so asking to check the branch is reasonable; repeated
lengthy instructions still occupy scarce handoff space. History is unavailable
inside this probe, while both pinned prompts refer to consulting it later.

The new arm used 192861 input tokens including cache versus 191845 old, and
5581 output versus 5498. These are observed run totals, not evidence of a
meaningful efficiency difference. Four repetitions of one task cannot support
a stable error-rate estimate or causal generalization to long coding tasks.
